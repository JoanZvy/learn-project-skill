# 项目文档大纲标准

## 1. 核心判据

大纲必须让读者仅看目录就能复述一次真实任务如何开始、推进和结束。组织优先级为：真实运行关系、输入输出与状态传递、业务阶段、模块或文件归属。

本文件只有抽象设计标准。实际目录必须从待分析项目提取，不能套用固定技术组合、业务阶段名称、文件列表或章节数量。

## 2. 锁定分析范围

在设计大纲前确定：

- 项目与包含、排除的目录范围。
- 当前源码版本，以及影响分析的未提交修改。
- 目标读者的基础和文档用途。
- 用户提供的补充资料、明确强调的核心能力与亮点。
- 可安全读取的材料、敏感配置边界及无法访问的内容。

范围内代码应完整阅读并记录覆盖情况。生成物、二进制、依赖副本或敏感文件不能假称读过；说明其用途、排除理由和影响。用户要求完整阅读而当前无法完成时，不提交伪装为全量分析的大纲。

## 3. 建立代码事实地图

按职责定位材料，再沿真实调用关系深入，不根据文件名推断行为。

| 阅读对象 | 必须确认的关系 |
|---|---|
| 启动与运行单元 | 外部如何启动，实际入口在哪里，哪些入口只是候选 |
| 配置与初始化 | 参数如何合并，依赖如何建立，缺失时怎样结束或降级 |
| 输入与调度 | 数据如何进入，谁创建处理对象，框架如何触发项目函数 |
| 核心处理 | 输入如何转换，判断如何分流，哪些函数负责阶段编排 |
| 状态与存储 | 状态由谁持有、谁更新、如何跨阶段传递，是否持久化 |
| 外部边界 | 交互输入输出、调用能力、鉴权来源及失败影响 |
| 并发与资源 | 执行主体、共享对象、持有范围、退出及清理 |
| 测试与部署资料 | 测试验证什么，哪些依赖被替代，部署事实有哪些证据 |

把已定义但未被所述入口调用的代码单独记录；资料表达的产品意图与当前实现分开。

## 4. 提取生命周期与分支

先确定“一次任务”的输入、开始条件、成功或失败结束条件，再追踪中间的真实处理阶段。

每个阶段记录：触发条件、调用者、执行主体、输入、主要转换、状态变化、输出接收者，以及分流和结束路径。相邻步骤没有直接传参时，只说明控制流关系，不虚构数据依赖。

同步调用、异步启动、回调执行和跨进程通信须分清。多个独立运行单元分别建立主线，只通过可证实的通信连接；不能画成并不存在的单一串行调用。

过滤、缓存命中、校验失败、控制操作、重试和降级等分支，放回实际分叉位置。只有跨阶段的共同机制才在主线后汇总，且回指首次出现的位置。

## 5. 划分章节

优先按阶段职责、输入输出形态、状态所有权、执行主体、长循环或资源生命周期的变化分章。

- 不把每个函数独立变成一章，也不把多条复杂链压成一个概述。
- 同一外层函数中连续的处理步骤，优先用同章小节承接。
- 确需跨章时，记录首次介绍位置和后续接续调用点；首次进入仍需建立完整函数全貌。
- 主流程和关键机制占主要篇幅，风险、测试、部署和接管建议作为必要补充。
- 核心深入对象由项目职责、复杂度、用户强调的能力及真实亮点决定，不按技术名称预选。
- 章数由真实复杂度和阅读连续性决定，不以历史项目或预设配额约束。

## 6. 章节设计合同

每章的要点必须足以回答以下问题，但此时不展开正文：

1. 本章处于哪一阶段，解决什么问题？
2. 从哪个真实入口、类型或函数开始，谁让它执行？
3. 输入来自哪里，读者已经掌握哪些前置对象或状态？
4. 主要处理、关键状态和需要深入的机制是什么？
5. 正常、失败、跳过、降级、超时或并发分支有哪些？
6. 输出交给谁，任务是在这里结束还是进入下一章？
7. 哪些结论是源码事实，哪些依赖外部环境或待确认资料？

正式大纲中的条目要落到当前项目的真实符号和对象。抽象标准用于指导分析，不能把这些问题原封不动当成空洞要点交付。

## 7. 完整大纲的交付结构

按以下顺序交付：

1. 阅读范围、版本、覆盖限制和读者定位。
2. 组织原则，说明为什么按该生命周期排列。
3. 分部分、分章节的完整目录及每章分析要点。
4. 总体运行关系，明确主要分支、异步交接和结束点。
5. 章节之间的输入输出及状态接续关系。
6. 关键不确定性与明确的待确认事项。
7. 声明当前只提交大纲，等待用户确认或修改。

可按职责考虑范围与任务定义、输入接入、关键处理、输出与结束、证据复盘和接管验证，但不是固定目录。不存在的阶段不补造，真实存在的重要阶段不能为简短而省略。

## 8. 大纲验收

| 检查维度 | 合格条件 |
|---|---|
| 阅读覆盖 | 明确哪些已读、哪些受限，不用局部阅读冒充完整分析 |
| 流程主线 | 从启动或输入到结果及结束，关键运行关系连续 |
| 章节具体性 | 每章具有真实入口、对象、处理和去向，不只有技术名词 |
| 分支位置 | 主路、旁路、异步与失败路径在实际位置交代 |
| 上下游关系 | 前章留下的结果能接到后章，缺直接传参时不虚构依赖 |
| 函数全貌 | 阶段编排函数有首次完整介绍位置，跨章有接续点 |
| 核心覆盖 | 重要职责及用户强调的能力有明确展开位置 |
| 证据边界 | 当前实现、需求意图、推断和部署事实没有混写 |
| 输出阶段 | 没有越过审批提前生成正文 |

任何一项不满足，先调整当前大纲再交付。审批后以确认版为骨架；深读发现实质性事实错误，记录影响并按用户授权调整，不为保留目录而编造正文。
